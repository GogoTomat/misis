# Storage architecture: <название проекта>

Заполняется для каждого сервиса. Короткий ответ — нормально, если он осознанный.

## Сервис: <имя>

| Пункт | Ответ |
|---|---|
| Владение | Какие данные принадлежат сервису. Кто ещё их читает и через что: API, события, проекция |
| Хранилище | Какое и почему. Для каждого дополнительного хранилища — задача, которую основное не решает |
| Основные запросы | 3–5 самых частых запросов и индекс под каждый |
| Транзакции | Что меняется атомарно внутри сервиса. Какие операции пересекают границу (кандидаты на Saga) |
| Отказоустойчивость | Реплики (синхронные/асинхронные), бэкап, допустимая потеря данных (RPO) и время восстановления (RTO) |
| Масштабирование | Ожидаемый объём, нужны ли реплики для чтения, какое поле станет ключом шардирования |
| Изменение схемы | Инструмент миграций, где лежат миграции, как выкатываются ломающие изменения |

## Пример: Orders

| Пункт | Ответ |
|---|---|
| Владение | orders, order_lines, order_status_history. Покупатель и каталог читают заказы через API, доставка и уведомления получают события OrderPlaced и OrderPaid |
| Хранилище | PostgreSQL, отдельная база `orders`, пользователь `orders_svc`. Нужны атомарное создание заказа с позициями и отчётные запросы по статусам и датам |
| Основные запросы | Заказы покупателя по дате — `(customer_id, created_at)`. Ожидающие оплаты для фоновой задачи — частичный `(created_at) WHERE status = 'pending'`. Поиск по номеру — уникальный `(number)` |
| Транзакции | Заказ + позиции — одна локальная транзакция. Резерв на складе и оплата — через границу сервиса, Saga (тема 7) |
| Отказоустойчивость | Учебный проект: бэкап раз в сутки, RPO — сутки. В продакшене: одна синхронная реплика, RPO близко к нулю |
| Масштабирование | Реплики не нужны. Идентификаторы — UUIDv7. Будущий ключ шардирования — `customer_id` |
| Изменение схемы | Alembic в репозитории сервиса, ломающие изменения — через expand and contract |
